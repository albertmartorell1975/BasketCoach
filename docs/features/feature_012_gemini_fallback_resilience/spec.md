# Feature Specification: Gemini Fallback & DevExpert Subscription Expiration Resilience

> 🔵 **Generated by**: `[PLANNER · workflow-planner]` (Updated per Human Guidance Checkpoint)

## 1. Source Feature & Idea Diagnosis
* **`id`:** `feature_012_gemini_fallback_resilience`
* **`area`:** `data`
* **`depends_on`:** `["feature_010_chat_integration", "feature_011_chat_improvement_areas"]`
* **`status`:** `accepted`
* **`module_topology`:** `Layer-Based (:domain, :usecases, :data, :app)`
* **Objective:** Implement seamless resilience and automatic fallback to Google Gemini when DevExpert subscription expires, returns authorization/quota errors (HTTP 401 Unauthorized, HTTP 402 Payment Required, HTTP 403 Forbidden, HTTP 429 Too Many Requests), suffers server outages (HTTP 5xx: 500, 502, 503, 504), or encounters network timeouts (`SocketTimeoutException` / `IOException`), covering BOTH AI inferences:
  1. Tactical relevance guardrail: DevExpert Decisions ('jev' model) -> Gemini JSON domain classifier fallback.
  2. Generative inference: DevExpert chat completions ('chat'/'chat-pro') -> Gemini chat completions ('gemini-2.5-flash').
  Also support direct startup with Gemini when DevExpert key is missing or invalid, and graceful UI error states when both providers fail.
* **Identified Ambiguities / Assumptions:**
  - *Failover Trigger Conditions*:
    - **Auth & Subscription**: HTTP 401 Unauthorized (expired/invalid key), HTTP 402 Payment Required (subscription expired/quota depleted), HTTP 403 Forbidden (account suspended).
    - **Rate Limit & Quota**: HTTP 429 Too Many Requests (rate limit reached).
    - **Server Outages**: HTTP 500, 502, 503, 504 (DevExpert server failure/maintenance).
    - **Network Failures**: `SocketTimeoutException` and `IOException` (timeout / unreachable host).
    - *Non-failover*: Client-side bad requests (HTTP 400, 422) indicating malformed client payload should not trigger failover.
  - *Failover Latching*: Once DevExpert fails with an auth/subscription or server error, `AiRemoteDataSourceImpl` latches `activeConfig` to Gemini for subsequent requests in the session to avoid duplicate failing round-trips and timeouts.
  - *Model Mapping*: DevExpert models (`"chat"`, `"chat-pro"`, `"jev"`) are not recognized by Gemini. When falling back, the request `model` parameter is translated to `fallbackConfig.model` (`"gemini-2.5-flash"`).
  - *Direct Startup*: If DevExpert key is blank/missing or placeholder, the app directly boots using Gemini without attempting DevExpert.
  - *Dual Failure UI State*: If both DevExpert and Gemini fail, `safeCall` maps the error to typed `DomainError.Network.*`, which `AnalysisViewModel` and `ChatViewModel` propagate to `AnalysisUiContent.Error` and `ChatUiContent.Error`. The UI renders `AnalysisErrorView` and `ChatErrorView` with localized explanation and a retry button.

## 2. Goal, Non-Goals & Acceptance Scenarios

### Goal
Ensure uninterrupted coaching workflow during Phase 1 tactical analysis and Phase 2 practice drill exploration in Chat and Analysis by automatically detecting expired DevExpert subscriptions, server outages (5xx), or network timeouts, and instantaneously failing over to Google Gemini without user intervention or crash dialogs. If both providers are unreachable, present a friendly, localized retry UI.

### Non-Goals
* No popup banners or intrusive alerts when failover occurs (the switch is 100% transparent to Coach Jordi).
* No changes to `:domain` contracts or entities.
* No changes to `:usecases` interactors.
* No persistence of provider fallback state to disk (in-memory session failover is sufficient).
* No automatic retry for client-side bad requests (HTTP 400).

### Job Story
When the DevExpert subscription expires, returns an authorization/quota error, or suffers a server outage/timeout during tactical analysis or conversational chat,
I want the application to automatically route tactical guardrails and generative inference to Google Gemini,
so I can continue preparing training sessions without interruption; and if both providers fail, I want a clear, friendly error UI with a retry option.

### Acceptance Scenarios

#### Scenario 1: Tactical Guardrail Fallback on DevExpert Subscription Expiration (HTTP 402/403) or Outage (5xx / Timeout)
* **Given** the app is configured with DevExpert as primary and Google Gemini as fallback
* **When** Coach Jordi submits a tactical chat query and DevExpert `/decisions` returns HTTP 402 Payment Required, HTTP 503 Service Unavailable, or throws a `SocketTimeoutException`
* **Then** `AiRemoteDataSourceImpl` catches the error, switches active provider to Gemini, executes the zero-shot JSON domain classifier via Gemini `/chat/completions` with model `"gemini-2.5-flash"`, correctly identifies the query as basketball relevant, and returns `true`.

#### Scenario 2: Generative Inference Fallback on DevExpert Unauthorized (HTTP 401) or Server Error (5xx)
* **Given** the app is configured with DevExpert as primary and Google Gemini as fallback
* **When** `generateAnalysis` or `generateChatResponse` is called and DevExpert `/chat/completions` returns HTTP 401 Unauthorized or HTTP 500 Internal Server Error
* **Then** `AiRemoteDataSourceImpl` catches the error, updates its active provider to Gemini, retries the request targeting Gemini's OpenAI-compatible endpoint with model `"gemini-2.5-flash"`, and returns the parsed DTO or generated response.

#### Scenario 3: Session Failover Latching
* **Given** an initial request encountered an HTTP 401/402/403/5xx or timeout from DevExpert and successfully fell back to Gemini
* **When** a subsequent analysis or chat request is dispatched in the same session
* **Then** `AiRemoteDataSourceImpl` immediately routes the request to Gemini with zero attempted round-trips or timeouts against DevExpert.

#### Scenario 4: Direct Startup with Gemini
* **Given** `DEVEXPERT_API_KEY` is blank or unset and a valid `GEMINI_API_KEY` is present
* **When** the app initializes and performs analysis or chat queries
* **Then** `NetworkModule` and `AiClientConfig.fromEnvironment()` provision Gemini directly, and `AiRemoteDataSourceImpl` executes all requests against Gemini with zero calls to DevExpert.

#### Scenario 5: Graceful Degradation on Dual Provider Failure (Friendly UI)
* **Given** both DevExpert and Gemini fail (e.g. DevExpert returns 402 and Gemini returns 503 or no Gemini key is provided)
* **When** Coach Jordi triggers analysis or chat message sending
* **Then** `AiRemoteDataSourceImpl` propagates the terminal exception, `AiAnalysisRepositoryImpl` / `ChatRepositoryImpl` translate it via `safeCall` into typed `DomainError.Network.*`, the ViewModel transitions to `Content.Error(domainError)`, and the UI displays `AnalysisErrorView` or `ChatErrorView` with a localized message in Catalan/Spanish and an active "Reintentar" button without crashing.

### API Design
* **DevExpert Inference Endpoints**:
  - `POST /v1/decisions` (`model = "jev"`)
  - `POST /v1/chat/completions` (`model = "chat"` / `"chat-pro"`)
* **Gemini Fallback Endpoints** (`https://generativelanguage.googleapis.com/v1beta/openai`):
  - Domain Classifier: `POST /chat/completions` (`model = "gemini-2.5-flash"`, `temperature = 0.0`, schema: `{"choice": "basketball_relevant"}`)
  - Generative Analysis: `POST /chat/completions` (`model = "gemini-2.5-flash"`, `temperature = 0.2`)
  - Generative Chat: `POST /chat/completions` (`model = "gemini-2.5-flash"`, `temperature = 0.7`)
* **Authentication**: HTTP Bearer token headers for both providers.
* **Failover Triggers**: HTTP 401, 402, 403, 429, 5xx (500, 502, 503, 504), and `IOException` (network timeouts).

### Persistence
* **No persistence changes required**. In-memory caches in `AiAnalysisLocalDataSource` and `ChatLocalDataSource` continue functioning identically.
