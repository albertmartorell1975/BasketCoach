Establish the Hilt Dependency Injection foundation across `:data`, `:usecases`, and `:app`, introduce `DashboardViewModel` adhering to the MVVM Passive Initialization Mandate (`loadDashboard()`) and the Hybrid UI State Pattern (`DashboardUiState` wrapping `DashboardUiContent.Loading`, `Success`, `Error` with `isRefreshing` overlay), implement `DashboardUiMapper` as the sole authority for mathematical transformations (computing the 3V-11D record, 21.4% win rate, 4 KPI pillars, 14-round evolution bar outcomes, and 16-column match table rows), and provide resilient loading and error recovery with retry mechanisms.

Target high-value logic: `DashboardUiMapperTest` (2 tests verifying math calculations and empty boundary conditions) and `DashboardViewModelTest` (2 tests verifying passive loading, success transition, and error/retry handling).

## 2. Goal, Non-Goals & Acceptance Scenarios

### Goal
Replace static preview data on the Phase 1 Dashboard with dynamic, reactive domain data loaded from `GetPhase1GamesUseCase`. Deliver a production-grade MVVM integration using Hilt DI, passive ViewModel lifecycle, atomic UDF state management, comprehensive error handling with retry capability, and exact mathematical calculation parity with authentic competition records.

### Non-Goals
* No modification to core domain business rules or existing JSON parser logic (static dataset `dataset.json` remains immutable).
* No AI analysis or chat integration (owned by `feature_009_analysis_integration` and `feature_010_chat_integration`).
* No dynamic match entry or local database sync (MVP dataset is static).
* No smartphone or portrait-oriented layouts (strict Tablet Landscape).

### Job Story
When Coach Jordi opens the BasketCoach Dashboard on the tablet,
I want the application to load the 14 Phase 1 competition matches asynchronously via `GetPhase1GamesUseCase` and compute authentic performance metrics,
so that Coach Jordi can review the real competitive baseline (3V-11D, 21.4% win rate, KPI differentials, evolution chart, and box scores) to plan Phase 2 practice microcycles.

### Acceptance Scenarios

#### Scenario 1: Happy Path — Loading and Rendering Real Phase 1 Data
* **Given** a functional `GetPhase1GamesUseCase` backed by `GameRepository` returning the 14 Phase 1 matches
* **When** Coach Jordi opens the Dashboard screen and `loadDashboard()` executes
* **Then** `DashboardViewModel` transitions from `DashboardUiContent.Loading` to `DashboardUiContent.Success`
* **And** `DashboardScreen` renders the authentic baseline hero card (3V-11D, 21.4%), 4 KPI cards (scoring 64.6 vs 73.7, rebounds 22.8 vs 30.6, eFG% 40.5%, AST/TO 0.59), 14-round evolution chart with win badges on J3/J9/J10, and 14-row statistical table across all 16 columns.

#### Scenario 2: Passive Initialization Mandate Compliance
* **Given** `DashboardViewModel` is instantiated
* **When** inspecting the initial UI state before any UI-driven event or `LaunchedEffect`
* **Then** no coroutines or repository queries have been triggered from constructor or `init`
* **And** `uiState.value.content` is strictly `DashboardUiContent.Loading` and `isRefreshing` is `false`.

#### Scenario 3: Error State & Retry Recovery
* **Given** `GetPhase1GamesUseCase` returns `Result.Error(DomainError.Local.NotFound)`
* **When** `loadDashboard()` executes
* **Then** `DashboardViewModel` emits `DashboardUiContent.Error(error = DomainError.Local.NotFound)`
* **And** `DashboardScreen` displays the error alert with a "Reintentar" retry button
* **When** Coach Jordi taps "Reintentar" and the use case returns `Result.Success`
* **Then** `DashboardViewModel` re-executes the load and transitions to `DashboardUiContent.Success`.

#### Scenario 4: Idempotent Concurrency & State Guarding
* **Given** `DashboardViewModel` is currently fetching game data (`isRefreshing == true`)
* **When** a duplicate `loadDashboard()` call is triggered concurrently
* **Then** the duplicate invocation is safely ignored, preventing redundant repository operations.

#### Scenario 5: Pure Kotlin JVM Layer Boundaries for `:usecases` & `:domain`
* **Given** the Hilt setup and constructor injection
* **When** inspecting `:domain` and `:usecases` dependencies
* **Then** `:domain` contains zero DI annotations, and `:usecases` uses exclusively JSR-330 `javax.inject.Inject` without any Android framework (`android.*`) or Hilt Gradle plugins.

#### Scenario 6: Bilingual Parity & Legibility
* **Given** new error and loading states
* **When** inspecting string resources across Catalan (`res/values/strings.xml`) and Spanish (`res/values-es/strings.xml`)
* **Then** 100% key parity is maintained, and all rendered typography complies with minimum `12.sp` (Constraint #16).
